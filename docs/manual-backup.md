# Manual Backup — administrator guide and API reference

Lets an administrator take a copy of the system database on demand and
download it.

> **A backup is a complete copy of the system.** It contains every user
> record, including email addresses and password hashes, alongside all
> strategic planning data. Treat a downloaded backup with the same care as
> the production database itself.

## Permissions

Three separate permissions, so that triggering a backup and removing one from
the server are distinct privileges.

| Code | Allows |
|---|---|
| `backups.view` | Seeing the list of backups and their metadata |
| `backups.create` | Running a backup |
| `backups.download` | Downloading a backup file |

Seeded by `PermissionSeeder` under the `backups` module. `Administrator`
receives all three via `RolePermissionSeeder`, which grants that role every
permission.

## Where files live

`storage/app/backups/`, which is outside the document root and therefore not
reachable by URL. The only route to a file is the download endpoint, which is
permission-checked and audited.

`storage/app/backups/.gitignore` keeps the directory in version control while
ignoring its contents. The service creates the directory at `0750` if it is
missing.

Filenames are generated by the server and never accepted from a caller:

```
spdms-backup-20260829-140233-k3n8ptqa.sql
```

The random suffix makes a filename unguessable and prevents a collision when
two backups start in the same second.

## Endpoints

```
GET  /api/backups                    list       backups.view
POST /api/backups                    create     backups.create
GET  /api/backups/{backup}/download  download   backups.download
```

All three sit behind `auth:api` and `auth.version`.

### Create

`POST /api/backups` takes no body. Returns **201** with the new record:

```json
{
  "success": true,
  "message": "Backup created successfully.",
  "data": {
    "backup_id": 12,
    "filename": "spdms-backup-20260829-140233-k3n8ptqa.sql",
    "size_bytes": 4404019,
    "size_label": "4.2 MB",
    "driver": "mysql",
    "status": "completed",
    "error_message": null,
    "downloadable": true,
    "created_by": { "user_id": 3, "name": "Jane Doe" },
    "created_at": "2026-08-29T14:02:33.000000Z"
  }
}
```

The request runs the dump synchronously, so it stays open until the backup
finishes. On a large database this can take minutes; the dump itself is
abandoned after 600 seconds.

A failure returns **500** and still records a row with `status: "failed"` and
a truncated, password-stripped `error_message`, so an administrator can see
that the attempt happened rather than wondering whether the click registered.
Any partial file is deleted — a half-written dump is worse than none, because
it looks restorable.

### Response codes

| Code | Meaning |
|---|---|
| `200` | List returned, or file streamed |
| `201` | Backup created |
| `401` | Not authenticated, or the token's `auth_version` is stale |
| `403` | Missing the permission for that specific operation |
| `404` | Backup row does not exist, the backup failed, or the file is gone from disk |
| `422` | Invalid `per_page` on the list endpoint |
| `500` | The dump failed; a `failed` row has been recorded |

## How the dump is taken

| Driver | Method |
|---|---|
| `mysql`, `mariadb` | `mysqldump` via `Illuminate\Support\Facades\Process` |
| `sqlite` | File copy — the database is a single file |
| anything else | Rejected with a clear error |

`mysqldump` runs with `--single-transaction --skip-lock-tables`, so the system
stays usable while a backup runs, and with `--routines --triggers --events`
so stored programs are included. `--no-tablespaces` avoids requiring the
`PROCESS` privilege.

**Credentials are never passed on the command line.** They are written to a
temporary `0600` defaults file, passed as `--defaults-extra-file=`, and
deleted in a `finally` block. Anything on the command line is visible to any
local user through the process list. The command is also built as an argument
array, so no value is ever parsed by a shell.

`mysqldump` must be on the `PATH` of the user running PHP. If it is not, the
backup fails and says so.

## Auditing

Every operation writes a row to `tbllog` against the acting administrator:

| Event | `states` | When |
|---|---|---|
| `backup.created` | `success` | A backup completed |
| `backup.failed` | `failed` | A backup failed |
| `backup.downloaded` | `success` | A file was sent to a browser |

The download entry is written *before* the file is streamed, since that is
the moment a full copy of the database leaves the server.

```json
{"event":"backup.downloaded","backup_id":12,"filename":"spdms-backup-20260829-140233-k3n8ptqa.sql"}
```

## Administrator UI

Technical Admin sidebar → **Manual Backup** (`/manual-backup`).

- **Create backup** asks for confirmation first, spelling out that the file
  contains every user account and password hash.
- While a backup runs the button shows progress, the table stays visible, and
  closing the tab triggers the browser's unsaved-work warning.
- Previous backups list the time, who ran it, the size and the status, with
  the filename shown underneath.
- Failed attempts appear in the list with their reason, rather than vanishing.
- **Download** is shown only to administrators holding `backups.download`;
  others see "Not permitted".
- Downloads are fetched as a blob so a 403 or a missing file appears as a
  message on the page instead of dumping JSON into a new tab.

## Restoring

Restoring is deliberately **not** exposed in the application — it overwrites
live data and belongs in a controlled maintenance window, run by someone with
server access.

```bash
# MySQL
mysql -u <user> -p <database> < spdms-backup-20260829-140233-k3n8ptqa.sql

# SQLite
cp spdms-backup-20260829-140233-k3n8ptqa.sqlite database/database.sqlite
```

Check the `driver` recorded against the backup before restoring, so a dump is
not restored with the wrong tool.

## Operational notes

- **Retention is not automated.** Nothing deletes old backups; the directory
  grows until someone prunes it. Worth a scheduled task if this sees regular
  use.
- **No scheduled backups.** This ticket covers manual backups only.
- **Long requests.** A large database may exceed the web server's timeout
  before PHP's. Moving the dump to a queued job would remove that ceiling and
  is the natural next step if it becomes a problem.

## Tests

`tests/Feature/BackupTest.php` covers authentication and each of the three
permissions separately, a successful backup, auditing, a failed backup being
recorded and reported, listing order and attribution, downloading with its
audit entry, 404s for missing files and failed backups, and — via a faked
process — that the MySQL password never reaches the command line and that the
credentials file is deleted afterwards.

```
php artisan test --filter=BackupTest
```
