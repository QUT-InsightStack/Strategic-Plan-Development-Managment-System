# Management interface on `codex/management-dashboard-restructure`

This branch starts from `develop` and incorporates the navigation, dashboard and read-only plan review from Meng Sun's `076dbc0` commit. Management pages open directly from the sidebar.

## Dashboard redesign (`dashboard` branch)

The Management Dashboard (`/management-dashboard`) is one page with a header ("Management Dashboard", planning-period selector, refresh and **Export Dashboard**), a row of six KPI cards, a shared filter bar and five tabs. No workflow statuses, thresholds or schema were added; the figures use the existing rules listed below.

- **KPI cards**: Strategic Plans (total, with a "By status" breakdown from `planning_status_label`); Objective Progress (completed / total and ongoing, objectives in approved plans); Alignment Coverage (objectives linked to both Agenda and PDP ÷ non-archived objectives); Inputs & Consolidation (share of inputs reviewed and the pending count; "No access" without input view permission); Awaiting Approval (plans with `approval_status = under_approval`); Overdue / Delayed (incomplete objectives in approved plans after the plan end date). There is no at-risk figure.
- **Filters**: Strategic Plan, Planning period, Office / Unit, Plan / Objective status, Approval status and Reset filters. Options come only from records the API returned. Planning periods are the distinct start–end year pairs of the returned plans (for example 2023–2028) and replace the former single-year filter. Office / Unit uses the responsible-unit assignment and falls back to the objective's office text. Filters are stored in the URL (`filter_plan`, `period`, `office`, `filter_status`, `approval`) and are kept for the browser tab, so they persist across tabs and across `/management-dashboard`, `/management-approvals` and `/management-plan-review`. Changing tab does not reset them.
- **Overview**: a six-year stacked bar chart and a Progress Breakdown table for one planning period (Year 1 = start year). Each year counts objectives in approved plans as they stood at the end of that year (or today for the current year), rebuilt from `tblobjective_progress_updates`; future years have no bar. Delayed applies the existing overdue rule at that date, so it only appears for plans whose end date has passed. Not Started is shown as its own series so the totals add up. Without a chosen period or plan the earliest period in scope is used, and the card says so. Objectives with no history use their current progress from `progress_updated_at` onwards. The chart is inline SVG (`role="img"` with a text summary); the table is its accessible equivalent. Below it: Plan & Objective Progress (the existing per-plan monitoring view), Office / Unit Performance (objectives, completion %, alignment coverage %, inputs submitted / pending, overdue), Attention Required (overdue objectives, objectives missing Agenda / PDP links, pending inputs) and My Pending Actions (`GET /api/plan-reviews` items assigned to the user at the current stage, linking to the existing decision page).
- **Alignment & Performance**: Alignment Monitoring table (Strategic Objective, PDP Chapter, Presidential Agenda, Agency, status pill and missing links) under the chain *Presidential Agenda → PDP Chapter → DOST Strategic Objective → Agency Plan*, an Alignment Summary (mapped objectives with coverage bar, active agencies) and the full Office / Unit Performance table.
- **Inputs & Consolidation**: the read-only Input Review list plus a consolidation summary per office.
- **Reviews & Approvals**: Awaiting approval / Approved / Returned for correction lists (Returned = existing `rejected` status). Review / decide links appear only for the current stage's assigned reviewer; decisions stay on the existing decision page. `/management-approvals` redirects Management users to this tab (`?status=` becomes `&queue=`) and still serves assigned reviewers in other roles with the shared component.
- **Reports & Summary**: the report master; see [management-report.md](management-report.md).
- **Export Dashboard** downloads the current tab's main dataset as CSV (Overview: the six-year breakdown; Alignment: alignment rows; Inputs: submitted inputs; Reviews: plan approval statuses). It is disabled while that data is loading, has failed or is empty.
- **States**: cards and tables show skeleton placeholders while loading. Plans, objectives, assigned reviews, inputs and the progress timeline load independently; a failed source shows an error with Retry in the sections that use it and leaves the rest of the page working. Empty results say "No data in your authorised scope"; empty filtered results offer Clear filters; missing permission is reported separately.
- **Sidebar** (flat): Dashboard, Alignment & Performance, Inputs & Consolidation, Reviews & Approvals, Plan Review, Reports & Summary. Old links resolve: `?tab=dashboard` / `?tab=monitoring` → Overview, `?tab=alignment&section=agency` → Inputs & Consolidation.

New endpoint: `GET /api/management/progress-timeline?plan_id={id}` (read-only) returns the plan's start/end dates, its objectives (`objective_id`, `status`, `created_at`, current progress fields) and their progress history (`objective_id`, `new_percentage`, `new_status`, `created_at`, without reasons or updater details). It requires `strategic_objectives.view`, checks the plan is within the user's listing scope, and applies `StrategicPlanAuthorizationService::scopeObjectivesForUser`, the same rules as `GET /api/strategic-objectives`. It was added because the existing history endpoint requires `strategic_objectives.view_progress`, which Management roles do not have, and works one objective at a time. Tests: `tests/Feature/ManagementProgressTimelineTest.php`.

## Earlier changes

The notes below describe the previous restructure; where they differ from the redesign above (for example the separate Approve List, Monitoring and Input Review links, or KPI cards only in Reports), the redesign applies.

- **Approve List** (`/management-approvals`) separates pending, approved and returned-for-correction plans. It lists plans within the account's authorised scope with search and pagination. Only a review assigned to the current user links to the decision page. The existing decision API performs `approve` or `reject`; the interface describes `reject` as returning the plan for correction because a rejected submission can be resubmitted.
- **Planning Module** opens the same existing plan list with distinct plan-summary and objective-summary views. Both lists are searchable and paginated. The plan review page also shows plan comments when the account has `objective_comments.create`.
- **Alignment Review** and **Agency Input Review** are separate top-level sidebar links into the existing objective API alignment summary. The agency view filters the same Agenda/PDP/objective associations by responsible office. The older `/mappings?mode=view` page uses browser-local mappings and is not the management summary.
- **Monitoring** keeps the original per-plan progress view and adds plan level, parent plan, plan search, level filtering, pagination and an expandable objective breakdown. Parent rows include objectives under child plans. It reads progress fields from the objective API.
- **Reports & Summary** presents a list of report datasets. A reviewer can open paginated rows in the page and export each complete dataset as CSV.
- Management filters use authorised plan data: plan, planning period, Office/Unit, plan lifecycle status, objective progress status and approval status. Review lists also have period, Office/Unit and status filters.
- Reports include plan approvals, objective progress and alignment, Office/Unit performance, agency input consolidation, assigned approval queue and overdue objectives. An objective is **overdue** when incomplete after its plan end date. No at-risk threshold has been defined, so none is reported.
- Management sidebar links are flat and open their corresponding content directly. The redundant horizontal dashboard tabs were removed; the five strategic-planning KPI cards appear only in Reports & Summary.
- The existing management permission helper is retained. The local-storage-based dashboard aggregation, which was unused after the redesign, was removed.

## APIs and backend changes

- Existing APIs: `GET /api/strategic-plans`, `GET /api/strategic-objectives`, `GET /api/plan-reviews`, `GET /api/strategic-plans/{id}/approval`, `POST /api/strategic-plans/{id}/approval/decision`, and plan comment endpoints.
- Management can read submitted agency inputs through the existing `GET /api/implementation-inputs` endpoint only with `implementation_inputs.view` and `implementation_inputs.view_all`. Migration `2026_10_06_000002_grant_management_input_read` grants those permissions to Management, Executive, Management / Executive, and Division Head roles; it was applied to the local database on 6 October 2026. The backend limits those inputs to authorised plans. Management does not receive input-review permission.
- A migration makes `responsible_unit_id` nullable on plan comments and grants management roles `objective_comments.create`. This lets management users comment without being assigned an agency unit. Deploying the comment feature requires applying this migration.
- The approval backend has statuses `under_approval`, `approved`, `rejected`. There is no distinct `returned` status or `return` decision. If the project needs "returned" to differ from "rejected" in workflow rules or reports, extend the schema, service, API, and tracking UI together.
- `GET /api/plan-reviews` only returns currently assigned pending submissions. The approved and returned tabs therefore show the current status of all authorised plans, not a history of decisions personally made by the current reviewer. A reviewer-specific history endpoint would be needed for that view.
- Approval and return buttons render only for the current stage's assigned reviewer. Management oversight pages contain no delete, user administration, approval governance or technical maintenance controls. Those remain on existing pages behind their own permissions.

## Data notes

The pages use objective `progress_percentage`, `progress_status`, `progress_updated_at`, Agenda/PDP relations, and plan `parents` supplied by the backend. They no longer derive management summaries from browser local storage. Planning-period filters select plans whose start and end years match the chosen period; other filters apply to the displayed records and exported CSV.

Agenda and PDP are separate objective relations in the current backend. The alignment summary lists those associations on one objective row; it cannot certify a specific Agenda → PDP pair without an explicit combined mapping relation/API.
