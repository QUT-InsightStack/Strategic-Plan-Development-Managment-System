# Manage Profile — editable and restricted fields

Covers the self-service profile: what a signed-in user may change about their
own account, what they may not, and why.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/auth/me` | Returns the authenticated user's profile and effective permissions |
| `PUT` | `/api/auth/profile` | Updates the authenticated user's own profile |
| `POST` | `/api/auth/profile/photo` | Uploads a profile photo (multipart) |
| `DELETE` | `/api/auth/profile/photo` | Removes the profile photo |

Both sit behind `auth:api` and `auth.version`. The user is always resolved
from the JWT, never from request input, so neither endpoint can be pointed at
another account.

## Editable fields

A user may change these on their own profile.

| Field | Rules |
|---|---|
| `first_name` | string, max 255 |
| `last_name` | nullable, string, max 255 |
| `email` | valid email, max 255, unique across `tblusers` (own address ignored) |
| `mobile` | nullable, string, max 20 |
| `address` | nullable, string, max 255 |
| `gender` | nullable, boolean |
| `date_of_birth` | nullable, date, before today |
| `designation` | nullable, string, max 255 |

All fields use `sometimes`, so a partial update leaves omitted fields untouched.

## Restricted fields

These are administrator-controlled. Sending any of them to
`PUT /api/auth/profile` returns **422** with a validation error naming the
field. They are rejected rather than silently dropped, so a caller never
receives a success response for a change that did not happen.

| Field | Why | Where it is changed instead |
|---|---|---|
| `role_id` | Privilege escalation | `PUT /api/users/{user}/role` |
| `status` | Account suspension is an administrative act | `PATCH /api/users/{user}/status` |
| `password` | Requires current-password confirmation | Change password page |
| `user_id` | Identity cannot be reassigned | — |
| `auth_version` | Session invalidation is system-controlled | — |
| `email_verified_at` | System-controlled | — |
| `department` | Organisational structure | `PUT /api/users/{user}` (admin) |
| `unit` | Organisational structure | `PUT /api/users/{user}` (admin) |
| `office` | Organisational structure | `PUT /api/users/{user}` (admin) |
| `position` | Organisational structure | `PUT /api/users/{user}` (admin) |
| `profile_picture` | It is a file, not a string | `POST /api/auth/profile/photo` |

The canonical list lives in
`App\Http\Requests\UpdateProfileRequest::RESTRICTED_FIELDS`. Update that
constant and this table together.

## Profile photo

The photo is a file, so it has its own endpoint rather than travelling as a
string through `PUT /api/auth/profile`.

**This previously did not work at all.** The page read the chosen file as a
base64 data URL and sent it as `profile_picture`. That column is
`VARCHAR(255)` and an encoded photo runs to tens of thousands of characters,
so on MySQL in strict mode every upload failed with
`SQLSTATE[22001]: String data, right truncated`. The column now holds a short
path and the image lives on disk.

### Uploading

`POST /api/auth/profile/photo`, `multipart/form-data`, field name `photo`.

| Rule | Value |
|---|---|
| Types | JPG, PNG or WebP |
| Maximum size | 2 MB |
| Dimensions | between 32 and 4000 pixels on each side |

The `image` rule reads the file with `getimagesize()`, so a script renamed to
`.jpg` is rejected whatever content type the client claims.

The stored filename is **generated by the server** — 40 random characters plus
an extension derived from the file's own contents. A client-supplied name is
never used: it could carry a path, a second extension, or characters the
filesystem treats specially.

Files are written to the `public` disk under `avatars/`, and the user record
stores `/storage/avatars/<name>.<ext>`.

Replacing a photo deletes the previous file, but only after the new one is
saved, so a failed write never leaves someone with no photo. Only paths under
`/storage/avatars/` are deleted — an external URL, or a value left over from
before photos were files, is left alone.

### Removing

`DELETE /api/auth/profile/photo` clears the column, deletes the file and
reverts the page to the default avatar.

### Response codes

| Code | Meaning |
|---|---|
| `200` | Uploaded or removed; the body carries the updated user |
| `401` | Not authenticated, or the token's `auth_version` is stale |
| `422` | Not an image, wrong type, too large, or outside the size limits |

### Deployment

`php artisan storage:link` must have been run, or stored photos will not be
reachable. The `public` disk writes to `storage/app/public`, which that
command exposes as `public/storage`.

## `designation` vs `position`

Both hold a job title, and the distinction is deliberate:

- **`designation`** — self-service. What the user chooses to display.
- **`position`** — administrator-maintained. Part of organisational placement,
  used by the admin user search filters alongside department, unit and office.

## Auditing

A successful update writes one row to `tbllog`:

- `user_id` — the user whose profile changed (always the caller)
- `operation` — `Profile updated: <changed field names>`
- `states` — `success`

Only fields whose values actually changed are listed. A request that resolves
to no change returns 200 with `"No changes were made."` and writes no audit row.

Photo changes are recorded separately, as `profile.photo_updated` and
`profile.photo_removed`.

## Response shape

`PUT /api/auth/profile` returns the user via `UserResource`, which exposes only
the profile fields listed above plus `role`. `role` is `null` for a user with
no role assigned.

`GET /api/auth/me` currently returns the model's full attribute set plus a
`permissions` array, because the sign-in flow reads role and permission data
from it. `password` and `remember_token` are excluded by the model's `$hidden`,
but the response is wider than `UserResource`. Narrowing it would change the
contract the login flow depends on, so it is left unchanged here.

## The profile page

`/profile`, built by `resources/js/profile-app.js`.

- **Save is disabled until something changes**, and again while a save is in
  flight, so the same edit cannot be submitted twice.
- **Reset** asks for confirmation when there are unsaved changes, and says so
  plainly when there are none.
- Leaving the page with unsaved changes triggers the browser's own warning.
- Field errors are tied to their input with `aria-invalid` and
  `aria-describedby`, and are only rendered when there is something to say.
- The photo panel validates type and size before uploading, shows progress
  while it works, and offers **Remove photo** once one is set.

## Tests

`tests/Feature/ProfileTest.php` covers:

- Page availability and authentication requirements
- Viewing own profile; password not exposed
- Valid updates, partial updates leaving other fields untouched
- Validation: invalid email, duplicate email, own email permitted, overlong designation
- Restricted fields rejected: role, status, password, organisational fields
- A user cannot update another user's record
- Audit row written on change

`tests/Feature/ProfilePhotoTest.php` covers the photo endpoints: authentication, storing a valid image, the server-generated filename, rejection of non-images (including one claiming to be a JPEG), oversized files and a missing file, auditing, replacement deleting the previous file, removal, files outside the avatars directory being left alone, isolation between users, and the profile endpoint refusing `profile_picture`.

Its image fixtures need the GD extension, which `UploadedFile::fake()->image()`
relies on.

Run with:

```
php artisan test --filter=ProfileTest
php artisan test --filter=ProfilePhotoTest
```
